# Empirical Verification

Companion document to `proposal_kv.md` ("External VEX Ingestion for Kubescape Vulnerability Scanning"). Moved out of the main proposal to keep that document focused on the design itself; every "see Empirical Verification finding N" cross-reference in `proposal_kv.md` points here.

Several of the doubts raised during proposal development don't need a maintainer decision — they're correctness questions answerable by testing against real vendor data. On 2026-08-14 five of them were tested directly, and on 2026-08-18 all seven findings below were independently re-verified live against today's real data (scripts, raw fetched samples, and full write-ups in the companion `vex-ingestion_testing` repo — https://github.com/rootp1/vex-ingestion_testing — one subdirectory per test). Every claim below is backed by a live fetch or a locally built/run binary — not a static reading of documentation. Findings 1-2 and 4 are directly load-bearing for v1 (OpenVEX). Findings 3, 5, and 7 used real Red Hat CSAF data as the richest available test fixture and are forward-looking validation for the future CSAF follow-up (not blocking v1), except where noted that their underlying principle (digest/PURL matching) also governs v1's own OpenVEX product matching.

| # | Doubt tested | Method | Result |
|---|---|---|---|
| 1 | Storage shape | Fetched real Red Hat CSAF docs (64,242-file feed as of 2026-08-18; sampled files up to 34.8MB, one covering 15,632 products) and confirmed Chainguard/Wolfi has no static per-image feed at all. | Reusing `OpenVulnerabilityExchangeContainer` unmodified does not work — real vendor shapes are the opposite of one-doc-per-image. **Directly confirmed on v1's own data too**: the real Chainguard Libraries OpenVEX feed (v1's mandatory e2e source) is organized per-package, not per-image — see finding 4. A reshape-on-ingest / product-indexed layer is required for v1, not just for a future CSAF follow-up. |
| 2 | Grype version | Built kubevuln's exact pinned Grype (`v0.99.1`) from source; scanned `alpine:3.18` for real (14 CVE matches, re-confirmed unchanged 2026-08-18); built a real OpenVEX doc marking a found CVE `not_affected`; re-scanned with `--vex`. A real CSAF doc was also tested (`known_not_affected`) as forward-looking validation for the future CSAF follow-up. | Both formats correctly moved matches into `ignoredMatches` with proper `appliedIgnoreRules` on the currently pinned version. No Grype upgrade required for v1's OpenVEX path. Grype's OpenVEX matching keys off the image's RepoDigest/synthesized `pkg:oci/...` purl — the normalizer must reproduce that exact identifier format. |
| 3 | Scope matching (forward-looking for CSAF; underlying principle applies to v1) | Fetched the real Red Hat CSAF/VEX document for CVE-2024-6119 (928 product-tree entries: 18 `known_affected`, 799 `known_not_affected`, 111 `fixed` — corrected from an earlier arithmetic error). | 179 distinct repo names recur across multiple different SHA256 digests within `known_not_affected`/`fixed` alone (e.g. `openshift4/aws-kms-encryption-provider-rhel9` at 4 different digests) — image-reference globbing alone cannot distinguish between them. Digest/PURL matching is required for correctness, not a hypothetical edge case — and this governs v1's own OpenVEX product matching just as much as any future CSAF ingestion. |
| 4 | Dedup key | Fetched 5 real Red Hat CSAF documents live (re-confirmed unchanged 2026-08-18, one revised again since the original test); inspected `document.tracking.id`/`version`/`revision_history` across revisions; fetched a real Chainguard Libraries OpenVEX document (`libraries.cgr.dev/openvex/v1/pypi/werkzeug.openvex.json`) and inspected its statement-identity shape directly, rather than the OpenVEX spec's abstract example. | Red Hat revises documents in place rather than reissuing new files — a pure content hash would wrongly treat every revision as a new statement. Neither CSAF nor OpenVEX define a per-statement ID — confirmed on the real Chainguard Libraries document (`{vulnerability, products, status, timestamp, last_updated}`, no `id` field). 99% of real leaf products (2143/2163) carry usable PURLs in the Red Hat sample. The real Chainguard document has a `version` counter but no `revision_history` array, unlike CSAF. Recommended key: `hash(source, document ID, CVE, sorted product PURLs, status)`, tracking `version`/`revision_history` (where available) separately. |
| 5 | Feed volume (CSAF follow-up only — not a v1 concern) | Fetched Red Hat's `changes.csv` (64,243 timestamped documents as of 2026-08-18); sampled document sizes for an average; computed totals and windowed change rates. | Full feed ≈15-21GB depending on sampling. Only ~0.45-0.9% of documents change in any 6-hour window. `changes.csv` should be the sync cursor for the future Red Hat CSAF follow-up. **Not a v1 concern**: v1's own OpenVEX sources (Chainguard Libraries, Ubuntu) are small enough for full-refetch-per-cycle — see Sync cadence in `proposal_kv.md`. |

**A sixth, unplanned finding** came out of chasing the "Supported feeds" doubt further after the initial pass looked wrong on first read. Sequence of verification, each step independently checked rather than trusted from the previous step's inference:

1. Built `wolfictl` from source (`go build`, cloned `wolfi-dev/wolfictl`) and ran `wolfictl vex package` against a real melange config (`openssl.yaml` from `wolfi-dev/os`) — silent, empty output.
2. Read the actual source (`pkg/cli/vex.go`): both `vex package` and `vex sbom` are no-op stubs — `RunE: func(...) error { log.Print("Did nothing!"); return nil }`, marked `Deprecated`.
3. Traced git history to the exact commit that did this: `9364dfe9`, "Drop wolfictl vex", 2023-06-07 — Chainguard's own message: *"The vex command depends on things within melange that have been removed, and we no longer use the vex command ourselves, so we have to drop it."*
4. Built `cosign` from source and ran `cosign tree` / `cosign download attestation` directly against the real registry for `cgr.dev/chainguard/wolfi-base:latest` — decoded all three attached attestations: `https://slsa.dev/provenance/v1`, `https://spdx.dev/Document`, `https://apko.dev/image-configuration`. No VEX predicate type present.
5. Read Chainguard's own official scanner-integration guide (`chainguard-dev/vulnerability-scanner-support`) — for container images/Wolfi, it explicitly recommends the **OSV feed**, not VEX, and marks the older secdb (`packages.wolfi.dev/os/security.json`) deprecated.
6. Found and fetched a real, live OpenVEX feed that *does* exist, for a different Chainguard product: `https://libraries.cgr.dev/openvex/v1/index.json` (207 packages, most recently modified 2026-07-14). Cross-checked one real statement — CVE-2024-34069, `pypi/werkzeug` — against an independent third-party source (OSV.dev's public API): the CVE, its GHSA alias, and Chainguard's internal advisory ID all matched exactly. Also confirmed the Grype PR Chainguard's own doc cites (`anchore/grype#2886`) is real and merged.

**Conclusion:** no OpenVEX artifact exists anywhere in the Chainguard container-image/Wolfi ecosystem (not in a hosted feed, not in `wolfictl`, not as an OCI attestation on the image). A real OpenVEX feed does exist, but scoped to Chainguard Libraries (remediated PyPI/Java packages) — a different target than the proposal's original `chainguard-openvex` example assumed. The Chainguard example in `proposal_kv.md` has been corrected accordingly (see "Example: Chainguard Libraries OpenVEX"). **Per maintainer direction, v1 scope is OpenVEX ingestion only** — Chainguard Libraries OpenVEX is therefore the first mandatory v1 e2e feed, with a second confirmed below (finding 8). Red Hat CSAF, which required no correction and is genuinely the most mature/well-behaved feed of anything tested here, becomes the natural first CSAF follow-up instead, once CSAF ingestion is picked up as future work — alongside other CSAF vendors (Cisco, Siemens, Schneider Electric, SUSE) that publish the same format — see Future Work in `proposal_kv.md`.

**An eighth finding, verified live 2026-08-18**, closes the second mandatory-v1-feed question: does Ubuntu/Canonical actually run a real, live OpenVEX feed, as the earlier draft of this proposal assumed without checking? Verified directly rather than trusted: Canonical officially adopted OpenVEX starting with Ubuntu 24.10, with two live access points — a bulk feed (`https://security-metadata.canonical.com/vex/`) and per-CVE JSON files (`raw.githubusercontent.com/canonical/ubuntu-security-notices/main/vex/cve/{YEAR}/CVE-{ID}.json`). A real sample (`CVE-2025-5994.json`, 37,982 bytes, live-fetched) is valid OpenVEX 0.2.0, authored "Canonical Ltd.", `version: 5`, with two statements — `fixed` (154 products) and `under_investigation` (137 products) — using real Debian-style PURLs (`pkg:deb/ubuntu/unbound@1.13.1-1ubuntu5.15?arch=source&distro=jammy`), not container images. Like Chainguard Libraries, it carries a `version` counter but no `revision_history` array. **Conclusion:** the Ubuntu OpenVEX claim is real, not invented, and Ubuntu/Canonical becomes v1's second mandatory e2e feed alongside Chainguard Libraries — both real, live, and empirically confirmed end-to-end, keeping v1's OpenVEX-only scope to exactly two vendor integrations rather than one.

**A seventh finding, tested 2026-08-14, directly targets the Option A fallback trigger** ("Grype's `VexProcessor` input format or version compatibility could still surface a blocker" — see Scan Pipeline Join and Key Design Decisions: Code Reuse in `proposal_kv.md`). **This finding is not load-bearing for v1**: since v1 ingests OpenVEX only, a scan never needs to mix two VEXSource formats through one `vex.Processor`, so the mixed-format behavior below is retained purely as forward-looking groundwork for the future CSAF follow-up. Rather than leave that as a hedge, it was tested against the real pinned Grype v0.99.1 module (resolved from the local module cache, no network fetch needed) via a throwaway Go test:

1. `vex.NewProcessor(ProcessorOptions{Documents: []string{"/nonexistent/path.json"}})` → `unable to create VEX processor: VEX document ... not found`. Confirms `VexProcessor` has **no in-memory/byte-content API** — `Documents` must be real file paths on disk, resolved via `os.Stat` and format-sniffing functions that open the file. This validates `proposal_design.md` §4.2's original "writes to a per-scan temp directory" description over an earlier hedge in this project's drafts ("whatever in-memory or on-disk form Grype's VEX processor expects"); the `buildGrypeVEXProcessor` sketch's `cleanup func()` return value already implicitly assumed this.
2. A single real, valid OpenVEX document on disk → `NewProcessor` succeeds and constructs a working processor.
3. **New, previously undocumented in either proposal draft:** a `Documents` list mixing an OpenVEX file with a non-OpenVEX file (format sniffed only from `Documents[0]` — see `grype/vex/processor.go`'s `getVexImplementation`) fails at `ApplyVEX` time with `unable to detect document format`. A single `vex.Processor` **cannot span two VEXSource formats at once** — CSAF and OpenVEX documents applicable to the same scan must be grouped by format and run through the matcher via separate `ApplyVEX` passes (see `applyExternalVEXByFormat` in the Grype adapter code, Scan Pipeline Join in `proposal_kv.md`), not handed to one processor.
4. Diffing `grype/vex/processor.go` and the `VulnerabilityMatcher` struct between the pinned `v0.99.1` and the also-locally-cached `v0.104.1` shows the API is byte-for-byte identical across that range — no version-compatibility drift found.

**Conclusion:** both halves of the originally-named blocker condition are closed. Version compatibility is not a real risk in the tested range. The input-format constraint is real but was already anticipated by the temp-file design and is fully addressable — it only requires grouping applicable external VEX documents by format before constructing a `vex.Processor`, not abandoning Option A. The residual, narrower reasons Option B might still be needed are ones this test did not (and structurally could not) cover: whether kubevuln's scan-worker pods can write per-scan temp files under their actual pod security context, behavior at production scale (this test used one synthetic document, not hundreds), and any future Grype major-version break. Option B remains documented for those unknowns, not for the reasons originally listed.
